# ADR 0009: Refresh generated data only when its content changes

- **Status**: Accepted
- **Date**: 2026-10-19 (recorded as an ADR 2026-10-26)
- **Tracking issue**: [#1632](https://github.com/cncf/endusers/issues/1632)
  (no-op weekly refresh pull request); implemented in
  [#1653](https://github.com/cncf/endusers/pull/1653)
- **Related**:
  [ADR 0008](./0008-scope-agent-findings-to-user-observable-change.md)

## Context

Several files under `data/` are generated by scheduled workflows rather than
edited by hand: `community-groups.json` and `community-people.json` (weekly
"Refresh community profiles and group status"), `radar-reports.json` and
`case-studies.json` (their own refresh lanes), and others listed in the data
contribution model table in `CONTRIBUTING.md`. Each lane runs its collector,
validates and builds, and hands the working tree to
`peter-evans/create-pull-request`, which opens a pull request when anything
differs from `main`.

`check-community-group-links.mjs` originally wrote `data/community-groups.json`
on every successful run with a fresh `checkedAt` timestamp. Group status almost
never changes, so the weekly workflow opened a pull request every week whose
only diff was that timestamp (#1632). Each such PR ran the full required check
set, needed a human merge, and produced a `main` commit that the public
changelog (ADR 0003) would otherwise have to filter out. The radar and
case-study collectors had already solved the same problem by comparing their
generated payload with the committed file and exiting without writing when it
matched; the group checker was the outlier.

The timestamp also carried two conflicting meanings. `checkedAt` said when the
upstream check last ran, and `validate-community-groups.mjs` warned when that
was more than 60 days old. Once an unchanged check stops rewriting the file, the
only timestamp that can honestly live in the file is the one for when the
_published data_ last changed, and a staleness warning over it would fire
against perfectly healthy weekly checks.

## Decision drivers

- A scheduled refresh should cost reviewer time only when a reader would see a
  different page afterwards (the same bar ADR 0008 sets for agent findings).
- One rule for every collector, so a contributor who has read one refresh lane
  understands the others.
- A timestamp rendered on the site must mean one thing, and that meaning must be
  the one the file can actually keep accurate.

## Options considered

### Option A: Add a workflow conditional

Teach `refresh-community-people.yml` to skip the `create-pull-request` step when
`git diff` shows only the timestamp line. Fixes the symptom in one lane, leaves
the collector writing a file it then has to be told to ignore, and has to be
copied into every other lane. Rejected.

### Option B: Drop the timestamp from the generated file

No timestamp, no no-op diff. But the `GroupLinkStatus` component renders the
date so a reader knows how current the status is, and the validator uses it to
reject malformed or future-dated data. Rejected.

### Option C: Make the collector content-addressed

Compare the freshly generated payload with the committed one and leave the file
byte-for-byte untouched when they match; write a new timestamp only alongside
changed content. The workflow needs no change because `create-pull-request`
already does nothing when the tree is clean. This is what the radar and
case-study collectors already did. Chosen.

## Decision

Every scheduled collector that writes a file under `data/` follows the
content-only refresh rule:

1. **Write only on change.** Compare the newly generated payload with the
   committed file (excluding the envelope timestamp) and exit without writing
   when they match. Log that nothing changed; do not touch the file's mtime or
   bytes. `check-community-group-links.mjs`, `collect-radar-reports.mjs`,
   `collect-case-studies.mjs` and `fetch-community-people.mjs` all do this.
2. **The envelope timestamp records when the published data last changed**, not
   when the collector last ran. For the group report the field is renamed from
   `checkedAt` to `generatedAt` to match the radar and case-study catalogs, and
   the `GroupLinkStatus` panel reads "Upstream group status last updated on
   {date}". A legacy `checkedAt` file is migrated by the next run that writes;
   that one-time write is intentional even if statuses are unchanged.
3. **Validators do not warn on the age of a content timestamp.** They keep the
   strict ISO 8601 and not-in-the-future checks (see `checkIsoTimestamp` in
   `scripts/lib/validate-utils.mjs`) and drop the 60-day staleness warning from
   `validate-community-groups.mjs`. An old content timestamp is the expected
   state of data that rarely changes; it is not evidence that the refresh lane
   is broken.
4. **No workflow conditional.** The refresh workflows keep running validation,
   tests and the production build on every schedule; when the collector leaves
   the tree clean, `create-pull-request` opens nothing.
5. **Pipeline health is observed from the workflow, not the data file.** A
   collector that cannot verify anything (every check inconclusive) exits
   non-zero and leaves the previous file in place, which fails the workflow run.
   A healthy run that changes nothing is silent by design.

## Consequences

- The weekly community refresh opens a pull request only when a group is
  archived, renamed, removed or added, or a profile changes. #1632 is the last
  timestamp-only refresh PR.
- A new collector added to `data/` is expected to follow the same five points; a
  reviewer can cite this ADR rather than re-deriving the argument. A scheduled
  lane that opens no-op PRs is a defect against this ADR, not a new design
  question.
- `data/community-groups.json`'s `generatedAt` and the rendered "last updated
  on" date can legitimately be months old while the weekly check is green. Agent
  findings that an old `generatedAt` or `fetchedAt` means the data is stale, or
  that a staleness warning should be restored, are decided by this ADR; comment
  here rather than filing (ADR 0008).
- `validate-community-people.mjs` still carries a 45-day `warn`-severity
  staleness check on `fetchedAt`, written before `fetch-community-people.mjs`
  adopted content-only writes. Under point 3 that warning now measures how long
  the profiles have been unchanged, not whether the lane is healthy, and will
  fire against a working pipeline once profiles sit still for 45 days. Removing
  it is a follow-up change under this ADR; its comment already records that
  restoring `error` severity would be a maintainer call, and this ADR settles
  that question the other way.
- `CONTRIBUTING.md` describes the community-group checker as recording status
  and the weekly workflow as opening a PR "with the result"; that remains
  accurate because the result may be no diff.
